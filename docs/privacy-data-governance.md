# SAYNTAX privacy and data governance decision pass (PR-05A)

## PR-05B pilot policy and implementation status

The project owner subsequently approved these pilot choices: lesson command logging defaults off and is separate from voice use; raw audio is not retained by SAYNTAX after processing; voice logs are intended for 30-day retention; disability support notes are not collected in onboarding; school, grade, and goals remain optional; accessibility preferences remain stored; the ordinary admin dashboard shows aggregate counts rather than raw transcripts or profile rows; export and deletion are assisted requests during the pilot; legacy confidence/reflection collection remains inactive. The lesson and global voice controls now explain Groq, local ASR, and browser speech processing at the point of use. Existing database rows were not changed.

The 30-day log limit is a **policy target, not currently enforced by an automated job**. A request channel and operator procedure for export/deletion, provider-specific retention verification, live database/RLS checks, and backup handling still need release review. The inventory and proposed decisions below describe the earlier PR-05A source snapshot; statements about default-on logging, onboarding notes, and admin raw-log display are historical baseline findings.

Source snapshot: `main` at `5249fadedc942e3ad28b7dccf8ec68e9c8af456f` (2026-09-30). This is an engineering inventory and proposal, **not an approved retention policy or legal assessment**. No live Supabase rows, provider terms, backups, Vercel logs, or browser speech services were inspected. Decisions below need project-owner approval before real-user collection.

## What the source confirms

- Supabase Auth stores account credentials and session data. `auth.users` has a trigger that creates `public.users`; every personal table listed below references `public.users` with `ON DELETE CASCADE`. No user-facing export, account deletion, or row deletion path was found. Personal-table RLS has owner/admin `SELECT` and relevant inserts/updates, but no `DELETE` policy. The SQL cascade is a *conditional database path* if an authorized operator deletes the Auth user; it does not prove deployed cascade behavior or erase backups, logs, provider copies, or browser storage.
- Onboarding requires `display_name` for students and offers optional age range, grade, school, goals, and a 2,000-character disability support note. The current active lesson flow reads accessibility settings, but no active flow reads those optional profile fields. Admin RLS can read profiles and settings, although the current dashboard does not display them.
- Authenticated Lesson V2 writes `lesson_v2_progress`; running a program writes or updates `programs` and appends `program_runs`. The old `progress` route remains callable, and `confidence_checkins` remains in SQL, but no current Lesson V2 client uses either. Existing legacy rows cannot be assumed empty.
- Lesson voice logging is **on by default** (`voiceLoggingEnabled=true` and enabled when `scc_voice_logging_disabled` is absent). The lesson offers “Đồng ý học bằng giọng nói” and “Học nhưng tắt ghi log”; only the second disables logging. The preference and acknowledgement live in browser `localStorage`, not an account-level consent record. Turning logging off does not delete earlier rows; another device can start with logging on, while a shared browser can carry one learner's choice into another learner's session. `transcript`, lowercased `normalized_transcript`, and `parsed_action` can all contain the learner's words; normalization is not de-identification. Text commands may also enter this log through the same lesson pipeline.
- The lesson explains that audio is sent to the active recognition service but does not name Groq or explain browser-vendor processing in the visible lesson copy. The global voice control can start the microphone without that lesson acknowledgement. The README describes Groq cloud mode, local FastAPI mode, and browser Web Speech fallback, but README text is not a learner-facing notice.
- The current code does not write raw audio to the database. Next.js forwards a request body to Groq or the local server. Local FastAPI writes a temporary file and removes it in normal completion and handled-error paths; a process crash or external provider retention is outside that guarantee. Browser Web Speech processing depends on the browser/vendor. The operator must verify provider terms and deployment configuration before making a stronger promise.
- The admin dashboard displays recent raw transcripts (up to 50), top unsupported transcript text, recent run error messages, and recent V2 progress, plus counts. RLS grants admins `SELECT` on all personal tables, beyond what this dashboard currently renders. Operations logging writes event/status/phase metadata without request bodies; hosting-platform log retention is not set in this repository.

Retention durations are **undefined** throughout this repository. “Pre-pilot” is a proposed engineering action, not an approved policy.

## Confirmed gaps and release gate

1. **No approved retention schedule** for account data, sensitive profile fields, raw voice logs, run history, legacy rows, browser preferences, backups, or host logs. No automated retention purge is implemented.
2. **No dedicated learner-facing privacy notice** at sign-up or onboarding. The lesson banner is partial, and global voice can start outside that banner. README disclosure is for operators/developers, not learners.
3. **Transcript logging is default-on and browser-local preference only.** Consent to use voice is conflated with consent to retain text, and the admin dashboard renders raw transcripts. Disabling logging does not remove previously stored logs.
4. **No export, self-service account deletion, or documented assisted request path** exists. SQL cascades appear complete for personal tables only after authorized Auth-user deletion; deployed FK behavior, live RLS, backups, provider copies, and session revocation still need staging/operator verification.
5. **Sensitive optional onboarding fields have no visible current use.** The broad admin `SELECT` policies exceed the dashboard's current display needs. Legacy reflection and progress data may still exist in deployed Supabase.

For a real-user pilot, resolve the owner decisions below, publish the approved notice and voice/logging choice, establish a practical data-request/deletion route, and verify provider and staging behavior before opening registration. Keep `npm test` and the existing release gates; do not infer deployed policy from migration source alone.

## Proposed PR-05B implementation scope after decisions

Keep PR-05B to **collection and disclosure at the point of use**: add a Vietnamese privacy notice linked from sign-up/onboarding and both voice entry points; name the configured Groq/local/browser fallback paths and distinguish transient audio processing from stored text logs; make logging a separate explicit choice with an approved default; record the choice consistently for authenticated users; adjust only the optional onboarding fields the owner approves; limit raw transcript display to the approved admin scope. Likely files: `apps/web/app/sign-up/page.tsx`, `apps/web/app/onboarding/page.tsx`, `apps/web/features/onboarding/**`, `apps/web/features/lesson-v2/components/voice-lesson-client.tsx`, `apps/web/features/voice-control/components/global-voice-control.tsx`, `apps/web/app/admin/page.tsx`, and a new privacy route/document as approved. Any schema change for durable consent or access must be separately reviewed and migrated; do not alter lesson/parser/ASR behavior.

Follow PR-05B with a separately reviewable deletion/export implementation and a retention/backup operation slice once the owner selects those policies. Acceptance should include: logging remains off without explicit approved consent on a new device; both microphone entry points show the correct provider disclosure; declining logs still permits learning; no durable raw-audio archive is created and local temporary files are removed after handled requests; admin access matches approved scope; staging tests prove user data isolation, export completeness, Auth-user cascade, session revocation, and backup exceptions. Do not run a purge against existing rows until an inventory, notice, and rollback/export plan are approved.
